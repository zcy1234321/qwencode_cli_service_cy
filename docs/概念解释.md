# 概念解释：qwen serve、daemon 与 SDK

> 面向第一次接触本项目的人。配合 `架构图.png` 一起看效果更好。

## 一句话版本

- **daemon（守护进程）**：常驻后台、不随单次任务退出的服务进程
- **qwen serve**：一个具体的 daemon —— 把 qwen-code CLI 变成常驻推理服务
- **SDK（`qwen_serve_client`）**：访问这个服务的客户端 Python 库，几行代码发请求

三者关系：**SDK 是方向盘，daemon 是发动机**。SDK 让你用几行 Python 开车，daemon 是始终在运转、提供动力的常驻服务。

## 什么是 daemon

「daemon」就是**常驻后台、不随单次任务退出的服务进程**。和普通命令的区别：

| | 普通命令（`qwen`） | daemon（`qwen serve`） |
|---|---|---|
| 生命周期 | 一问一答，跑完就退出 | 启动后一直挂在后台 |
| 状态保持 | 每次重启重新加载 | 配置、会话、连接常驻内存 |
| 响应方式 | 每次调用重新启动进程 | 监听端口，请求来了即时处理 |
| 类比 | 每次去现场找临时工，干完解散 | 长期坐班的团队，派活就行 |

本项目里的 daemon 就是 `qwen serve`：启动后监听 `127.0.0.1:4170`，内部为**每个会话维护一个独立的 qwen 子进程**（首次建会话有启动开销；会话闲置超时会回收，重新使用时会冷启动重建）。

## qwen serve 和 SDK 的区别

**qwen serve 是"服务端"，SDK 是"客户端"，两者通过 HTTP/SSE 协议对话。**

| | qwen serve（daemon / 服务端） | SDK（`qwen_serve_client` / 客户端） |
|---|---|---|
| 角色 | 真正干活的推理引擎 | 帮你发请求的薄封装 |
| 形态 | 一个常驻进程，监听端口 | 一个 Python 库，`import` 就能用 |
| 干什么 | 模型调用、工具执行、MCP、Skills、权限审批、会话状态管理 | 把请求发到 daemon、把结果解析成 Python 对象 |
| 比喻 | 饭店的后厨 | 服务员 / 点菜 App |

### SDK 使用示例

```python
from qwen_serve_client import Client

client = Client(base_url="http://127.0.0.1:4170", token="xxx")
sid = client.create_session()
for chunk in client.run_turn(sid, "帮我改这个 bug"):
    print(chunk)
```

这几行代码背后发生的事：

1. SDK 把 `run_turn` 翻译成 HTTP 请求发给 daemon
2. daemon 找到（或启动）该会话的 qwen 子进程
3. 子进程调模型、按需执行工具
4. 结果通过 SSE 事件流推回
5. SDK 解析事件流，变成 Python 对象/生成器交给你

## 放到整体架构里

```
你的程序 ──HTTP/SSE──▶ qwen serve daemon ──HTTPS──▶ 模型厂商 API（Kimi…）
   │                        │
 SDK（客户端库）         常驻服务：会话、工具、审批
```

关键点：**N 个程序可以共用同一个 daemon**。每个程序带自己的 token 连上来，daemon 给每个会话独立隔离。实际部署中，在 daemon 前面还有一层 UI 网关（本项目 `qwen_serve_ui`），统一做鉴权、工具/路径白名单、配额和审计——参见《架构图》和《使用指南》。

没有 daemon 的模式下，每个程序要自己拉起完整的 qwen 进程、各自加载配置和 MCP——又慢又难管；daemon 模式让这一切集中、复用、可管。
